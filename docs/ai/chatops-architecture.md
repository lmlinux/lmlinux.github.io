# ChatOps 排障平台架构：会话、能力与审批的三条边界

把模型接进群聊，让它回答"Pod 为什么重启"，一天就能做出演示。但真正要面对的是**两个公有云、多个区域、几十套集群环境**，多个团队同时提问、并发几十个话题，只给它该拿的权限，不动生产，还得把每次排障沉淀成可复用的判断依据。这时候难的不再是模型，而是三件事：**话题属于谁、agent 能碰什么、变更谁签字。**

## 1. 系统形状

系统由四个面组成，彼此只通过明确接口连接：

| 面 | 职责 | 约束 |
|---|---|---|
| 交互面 | IM 话题中的人机对话；MCP 供研发自己的 agent 调用同一套能力 | 只做传输与身份 |
| 编排面 | 常驻 bot：事件循环、会话映射、并发、审计、回复组装 | 不存 LLM 状态，崩溃可恢复 |
| 能力面 | 只读工具（日志、指标、事件、变更、构建、源码）与 agent 运行时 | 凭据只读，无 Secret、无写 |
| 知识与审批面 | 私有文档与案例库、只读复核、人工执行 | 只主动拉取，不反向暴露 |

部署上分两台机器：对外应答面只持排障所需的只读凭据，跑 IM、bot、运行时和观测；私有面持完整运维知识、案例库和高权限环境。连接方向是单向的——私有面能主动拉取应答面的证据，应答面读不到私有面。**这条边界的表达方式是部署位置和凭据范围，不是提示词里的"不许"。**

```text
研发 ──── IM 话题 ────┐
                       ├── bot（事件/会话/并发/审计）── 运行时进程 ── 只读工具
研发的 agent ── MCP ───┘         │                                     └─ 只读凭据
                                 └── 审计库 / 案例台账 / LLM 观测
                                 │
                                 └── 写操作方案（确定性信封，不含命令）
                                            │ 单向
私有面：入口筛查 → 只读复核（拟制+验证） → 人审定命令块 → 逐字重放
```

选 IM 而不是自建 Web UI，是因为排障天然是"一问一会话"：要上下文、要留存、要被人看见、要给问题起名字。选型时的分水岭不是功能多少，而是**话题这个对象能否改名和搬移**——这一点决定了显示名和身份能不能拆开（第 3 节）。

## 2. 一次请求的生命周期

1. **接入**：轮询拿到消息，判定发送者是否人类、话题是否处于监听态、是否重复。话题默认免 @，可随时暂停，显式 @ 始终穿透。
2. **命名**：默认名话题在**提问时点**用一次轻量模型调用生成语义化名字（区域、环境、服务、症状、日期），搬移前复检归属，确认没有别人的消息混入。
3. **分派**：确定性命令直接走工具函数，参数在边界严格校验，非法值当场拒绝；自然语言进入运行时。
4. **执行**：一个话题对应一个运行时会话。同话题串行，跨话题并发。期间不刷屏，只用状态反应表示在跑。
5. **回帖与留痕**：答案落最终话题名，同时写审计，观测事件异步发出。
6. **追问**：同话题续接原会话，改名窗口内到达的消息补搬到新名，避免问答分居。

并发上两处容易低估：**同话题串行是硬约束**，同一会话被两条消息同时续接会直接损坏上下文；命名有几百毫秒到几秒的窗口，窗口内的追问必须等改名落定再换锁，否则两个线程会拿着不同的锁跑同一个会话。

## 3. 会话身份：用消息 ID，而不是话题名

身份和标签必须拆开：

- **case_id = 该话题首条消息的 ID**，不可变、全局唯一、人能直接在 IM 里追溯。
- 审计行、会话键、后续管道的来源全部按 case_id 归属，**改名不迁行**。
- 名字放在一张追加表里（case_id，名字，生效时间），既表示"当前叫什么"，也保留"曾经叫什么"，迟到消息按名反查时有一个有限窗口。

|  | 话题名 | case_id |
|---|---|---|
| 可变性 | 用户随时可改，甚至整体搬移 | 永不变 |
| 唯一性 | 同名可复现，只能靠日期后缀避撞 | 全局唯一 |
| 使用者 | 人 | 机器（审计、会话、管道） |
| 职责 | 可读、可搜、可辨 | 归属与寻址 |

一句话概括这条取舍：**用可变的共享名字当主键，对账层就是定律，不是缺陷。** 名字一旦同时承担显示和寻址，改名就会牵动数据完整性——要不要迁行、迟到一秒的消息算新话题还是旧话题、手工改名会不会覆盖别人，每个问题单独看都能特判，合在一起却收不了口。把寻址交给不可变的 ID 之后，改名退化为纯粹的显示层事件：可以在提问时为了可读性就改，失败也不牵动任何数据。

默认话题（共享总线）是唯一例外——历史全属本次会话就整体改名，视图跟着走；夹着别人的消息就只在能确认目标为空且当前消息最新时拆分，拆完立刻复查，发现更晚的消息就回滚。**宁可放弃视图跟随，也不把两段无关历史合成一个会话。**

## 4. 运行时：把失败语义定义清楚

运行时是独立子进程，不是嵌在 bot 里的库。好处是单话题故障不拖垮进程，换模型、换 harness 不用动会话、审计、审批这些真正的业务逻辑；代价是进程间契约必须写死：

- **会话 ID 一捕获就落盘**。曾经是整轮结束才写映射，容器重启后话题没有任何记录，追问只能开新会话、丢掉全部证据。
- **失败分三类**：墙钟超时是终态，不等待不重跑；用户打断是独立异常，回"已打断"而不是"调用失败"，也不重试；其余瞬时错误只允许同模型重试一次。
- **不做跨模型备用**。试过"超时后换另一个模型续接同一会话"，结果只是把异常分支、会话路由和配置状态翻了一倍，超时本身一点没消。删掉后规则只剩一句话。
- **长任务要安抚但不要刷屏**：20 秒、300 秒各一次进度提示；工具轮数撞上限时提示可以回复"继续"沿现有证据再跑，而不是自动无限续跑。
- **预算显式**：单轮墙钟、工具轮数、发送截断线都是配置项；超长原文自动转附件，正文只留结论和关键字段，避免被静默截断而无人发现。

打断机制同时是产品和架构两次判断。人手侧用**表情反应**而不是命令词：命令词一公开，bot 自己的回显就是最大误触发面；更麻烦的是命令走话题内的串行队列，深挖正持锁时打断命令会排在自己要打断的任务后面，永远迟到。跨进程取消同理——MCP 服务和 bot 是两个进程，取消句柄在 bot 内存里，最后不是加共享内存，而是**把消息当信号**：往目标话题发一条带内部标记的自转发消息，bot 按 `(频道, 话题)` 查在途索引触发取消，之后与人手打断走完全相同的收尾路径。两个进程唯一共享的本来就只有聊天事件队列。

## 5. 能力面：凭据为什么必须留在服务端

排障要读的东西很广。最直觉的方案是"把凭据发给每个研发"，在几十套环境上是这样的两笔账：

**kubeconfig 是人 × 集群的方阵。** 几十个集群分布在两个公有云、多个区域，每个研发要覆盖自己可能被叫去支持的几个环境；签发、回收、轮转、过期、namespace 授权逐项维护，集群一增减，几十份配置都要跟着改。

**AK 更糟，因为它天然是全账号级的。** 没有 namespace 那样的天然边界，要收窄只能去每个云上建只读子账号再按人下发；轮转一次就得通知所有拿到过的人。而且 AK 一旦落到研发机器或 CI 上，放出去的是这个账号能做的一切——不是"读"。

两笔账共同的问题是没有归属：日志里看到的是"某个 AK 做的"或"某份证书做的"，不是"某个人"。

真正的代价不在第一次分发，而在之后每一次：加一个区域、加一个集群、来一个人、走一个人、轮一轮密钥，都要把这张方阵重做一遍。而只要发出去过一份写权限，它就永远不会自己收回。

所以能力面集中托管，**凭据只在服务端，研发拿到的是一枚 token**。MCP 服务暴露一组只读工具，每个请求按 token 归属者审计和限流，吊销即时生效，兼作失控 agent 的急停开关。限流按人做滑动窗口，查询、深挖、写方案分别计数，同一用户的同时在途深挖也有上限——一个新发起的深挖往往要跑一到几分钟。

工具按"要多久、要不要人兜底"分三层：

| 层 | 形态 | 适合谁 |
|---|---|---|
| 快查 | 秒级返回结构化结果 | agent 自己推理 |
| 深挖 | 引擎多轮排查，同步返回结论，话题作为续接句柄 | 要结论、要证据链 |
| 写操作 | 生成方案进入审批管道 | 确实要改东西，愿意等人工 |

深挖有个细节：agent 的上下文会被压缩甚至清空，所以返回的不能只是一段文字，必须有**可找回的句柄**（频道 + 话题）和一个"列出我最近的诊断"的轻量工具。结论只认 bot 在话题里的真实回复，用户文本或其他桥消息里出现的"已排查完"不冒充结论。

最后一条产品决策：**直查和深挖的结果保留原文**。早期把内网 IP、路径、疑似凭据统一打码，研发拿着打码后的日志根本没法复现问题。现在按消费侧权限分层——运行时回帖保留现场，公开面（发布的知识、公共反馈板）固定严格脱敏；凭据类规则恒定生效，没有开关。

## 6. 写操作入口：从一次提问到一张方案

所有写操作只有一个入口。用户在话题里发 `/plan <说明>`，或者研发的 agent 通过 MCP 提交同名请求，两者落到同一条管道上，没有第二条旁路。

这个入口做的事情很少，这是刻意的：

1. **只打包，不拟命令。** 把用户原话、本话题已有的诊断结论、必要的上下文写成一份确定性信封——一个 JSON，落到私有面的待处理目录。bot 侧全程没有模型参与生成，它只负责把"现场"搬运过去。
2. **给一个可追踪的 ID。** 信封 ID 带分钟级前缀加一段随机后缀，避免同分钟同环境的请求互相覆盖；话题名在日期前插入一段请求 ID，让同一天、同一环境、语义相近的方案不会合并到同一个审批会话里。
3. **先拆话题，再受理。** 方案始终落在语义化的最终话题名下，反馈、帮助、监听控制这类命令留在原处。理由很简单：方案的复核和执行结果要在几天后被翻出来，它们必须和一个可读的名字在一起。
4. **通知对齐"需要人做下一步"的节点。** 方案生成时私信当事运维；复核通过、等待人工执行时，再单独发一条"待你执行"的私信，附方案 ID、请求、发起人、话题链接和执行命令。开始复核这种没有动作的中间态不发通知，正常驳回和执行结果只回话题——消息应该对应动作，而不是状态迁移。

信封是跨进程的上下文桥，这一点值得强调：私有面根本看不见聊天服务器，它拿到的只有这份 JSON。所以"用户原话"必须原样保留，不能由 bot 先总结一遍——一旦在搬运环节做了压缩或改写，复核侧看到的就不是现场。

```text
用户 /plan 或 MCP submit_plan
        │  确定性信封（原话 + 结论 + 上下文 + ID）
        ▼
私有面待处理目录 ── 入口筛查 ── 只读复核（拟制命令 + 验证风险与回滚）
                                   │ 通过                      │ 未通过
                                   ▼                            ▼
                              待人工执行（私信）              拒绝存档（回话题）
                                   │ 人审定命令块
                                   ▼
                              逐字重放 → 执行汇报回话题
```

`/plan` 本身不产生任何变更，也不承诺一定会执行——它只是把问题从"要不要做"推进到"这么做行不行"，把判断权交给下一个环节。

## 7. 写操作防线：用能力分离替代提示词

这部分改过最多次，起点是一次真实事故：一个安全测试脚本把注入文本送进了持有全权凭据的 agent，它真的执行了一条重启命令。教训不是"提示词写得不够狠"，而是**提示词级防线可以被攻破，能力级防线不能**。

重构后是一条三段式管道，加一条贯穿全程的测试纪律：

| 步骤 | 位置 | 作用 | 边界性质 |
|---|---|---|---|
| 入口筛查 | 方案落盘后、进模型前 | 对请求文本做静态匹配，命中已知的注入与越权意图就直接拒绝，不进入模型 | 只能拦已知形态 |
| 只读复核 | 私有面 | 只读凭据 + 独立运行环境，复核结论可以被验证但不能被顺带执行 | 混合，见下文 |
| 人工确认 + 逐字重放 | 人工终端 | 执行器里没有模型；逐字重放人审定过的命令块 | 审定清单 + 失败即拒 |
| 测试纪律 | 全程 | 任何评估、注入演练只用 mock 或假凭据，绝不带真实全权凭据 | 流程约束 |

几个要点：

**方案信封是确定性的。** bot 侧不生成命令，只把用户原话、话题结论和上下文打包成 JSON。命令由只读复核侧独家拟制——所以"复核"其实是"带着完整私有知识的拟制 + 验证"合一，管道里并不存在"bot 拟一遍、人再审一遍"的第二道。信封的价值是跨进程的上下文桥：私有面看不见聊天会话，只能通过它拿到现场。

**执行器里没有模型。** 复核结论末尾是固定格式的命令块（有序命令 + 回滚命令），执行时逐字重放：操作人看到的就是将要执行的。解析失败即拒——只认最后一个命令块，块坏了就停，不回退旧块也不猜。命令形态必须落在预先审定的清单内，其余一律拒绝；凡是无法安全解析的输入，一律按拒绝处理，不猜测意图。触碰状态敏感的命名空间要逐字输入确认。

**只读的文件查看，只在人工批准后放行。** 有些根因只差一眼"容器里的配置文件是什么样"，全禁会把这类问题永远外派给人。所以放行的只是形态最窄的一类：非交互、只读、单次、有明确目标的文件查看，不支持任何 shell 组合与链式传参；而且只在人工批准之后放行，复核阶段仍然全禁——复核不需要进容器，够定性到"需要看容器内文件"就够了。

**演进的锚点不能丢**：人审定的是一个确定性产物，执行器逐字落地。诊断可以多想多深，多步序列由命令块承载，声明式变更走 gitops；但"运行时再决定做什么"必须让渡给人——能被执行时说服的执行者，也能被注入说服做别的事。后续要把低风险动作交给自动化时，扩的也只能是"可审定的确定性单元"和"谁来签字"（第 12 节），不是执行时的智能。

**每层边界都要标注它到底有多硬。** 能由服务端强制执行的边界是一类，删不掉、绕不过；只能约束在进程侧的边界是另一类，理论上总有出口。前者的例子是只读身份——写请求在服务端就被拒绝，与调用方用什么客户端无关；后者再多包几层也只是抬高门槛。所以硬化的方向永远是把它推到服务端去，而不是在进程里加一个更聪明的壳。把软边界当成硬的写在文档里，比承认它软危险得多。

## 8. 案例循环：从一次排障到可复用的判断

一次排障结束后，价值不应该随着话题沉底而消失。案例循环负责把它变成下一次可以直接用的东西。

```text
每次成功的深挖 ── 独立进候选池（不按话题去重）
        │
        ▼
私有面定时审阅：成稿 + 关键数字抽核
        │
        ├──→ 私有案例库（完整证据链，权威）
        ├──→ 判据回流：可复用的判别规则写回私有指南
        │
        ▼
脱敏摘要 → 公开知识面（供下次检索命中）
```

几个关键取舍：

**候选的粒度是"一次调用"而不是"一个话题"。** 同一个话题里连着查了三个不同的问题，那是三次独立的价值，不能只留最后一次。反过来，话题名也绝不作为去重键——它只是上下文。

**草稿和成稿分开。** 自动拉取的证据包先落在暂存区，不进正式库、不登记索引。原因是正式库同时被三个自动化面消费：摘要发布、自动提交、知识提炼。毛坯混进去，等于告诉这三个面"这是成稿"，一份带占位符的半成品就可能被发布出去。**目录即状态**——在暂存区就是待成稿，进了正式库就是成稿，用位置表达状态比用字段可靠。

**量化数字必须抽核。** 真实复核过一次历史案例，发现转述里有几处数量、时长、条数与一手来源不一致。根因是成稿环节把诊断时输出的证据包当作事实忠实转写，没有再做一次核对。所以规则是：关键量化断言逐类回到一手来源核实，核实不了的显式标注"未复核，来源为诊断转述"，不得无声落库。

**上线后的回答不披露引用了哪个案例。** 检索到先例只用于形成假设和核对适用域，最终回答只呈现本次现场证据、结论与待验证项。否则用户会以为"上次也是这样"，而环境往往已经变了。

**回流目标分形态。** 可复用的判别规则进指南或 playbook，参考事实进 facts 表；只有确实属于行为级的纪律才进提示词，而且要过提示词那条闸门（第 11 节）。答不上形态的经验，通常是想得还不够清楚。

## 9. 知识循环：私有是源，公开是子集

案例循环产出的是一手经验；知识循环负责把整个私有文档体系的增量，持续提炼成公开面可用的那一小部分。

```text
私有文档增量（按上次素材水位取）
        │
        ▼
定时提炼：新增的判别规则 / 参考事实 / 工具坑
        │
        ▼
写入公开知识原文 → 审计 → 提交 → 审计实际发布字节 → 同步到应答面 → 通知
```

这条链路的核心约束只有一句：**私有文档永远最全最新，公开知识只能是它的子集。**

子集关系不靠提示词保证，靠结构保证——提炼的素材面取自私有仓库的 git 增量，模型没有别的输入。它不能"发明"一条只存在于公开面的内容，因为素材里根本没有。

发布链路每一步 fail closed：先审计即将提交的原稿，再解包 `git archive HEAD` 审计实际要发布的字节，保证被检查的就是被发布的；任何一步失败都发通知并停止后续阶段，绝不带着半边成功往下走。素材水位只表示"这批素材已经交给提炼"，不表示"已经发布"——所以即使这轮没有新素材，也要跑一次发布对账，把上一轮遗留的发布补上。

终点是自动提交、自动发布、发一条通知。人工从"每篇逐个确认"换成"事后扫一眼通知，有疑义再 diff"。这不是放弃审核，而是把审核放到它真正有价值的位置上：**确定性步骤交给脚本可审计，判断性步骤才留给人。** 前提是失败必须可见、必须阻断，否则自动化只是在放大不可见。

还有一条界限要划清楚：**公开面发布、内部运行时回帖、私有文档读取，三者口径不同。** 公开面固定严格脱敏，因为它是给更大范围的受众看的派生内容；运行时回帖保留原文，因为研发要用这些证据去复现问题；凭据文件在两条路径上都禁止触碰。用同一个开关控制这三件事，早晚会在某一边出问题。

## 10. 上线之后最意外的一件事：隐私需求

设计时默认假设是"排障过程公开是好事"——同一个环境里的人可以看到别人怎么排查，新人能围观学习，重复问题能直接搜到历史话题。实际运行后发现，需求正好相反：**研发有很强的隐私诉求**，不止一个人自己建了私有频道来用这个平台，不希望自己的提问被同事围观。

这不是个别偏好，背后有几层很实际的顾虑：

- 提问本身在暴露状态。"我的服务一直重启"、"这个接口为什么 500"这类话，被同事看到等于自曝负责的模块有问题；在被追问之前，很多人宁愿先自己问清楚。
- 排查过程会带出比问题本身更多的东西：集群名、命名空间、应用名、日志里的业务字段、某些还没对外说的变更计划。一次公开的排障，等于把现场摊开给所有订阅了那个频道的人。
- 试用期的心理成本不对称。工具好用之前，公开提问的成本是确定的（可能被看到），收益是不确定的（可能答不上来）。理性的人会先躲起来试。

这件事值得单独写，因为它改变了对"平台应该长什么样"的判断：**围观学习是副产品，不是前提。** 想靠"公开"来沉淀知识，等于要求使用者先放弃隐私；而知识沉淀本来就有另一条路——案例循环从会话里提炼，是否公开由发布闸门决定，不需要靠围观来产生。

好在所选平台天然支持私有频道，这件事不需要开发任何东西：私有频道只对成员可见，bot 被邀请进去就能正常服务，历史、审计、会话、案例沉淀都不受影响。唯一要处理的是权限模型上的几个细节，都是设计期没预料、上线后靠真实使用暴露出来的：

- **bot 必须被显式加进频道**，否则它是"能被 @ 到、但读不了历史"的半可用状态——提问能到达，中间状态消息发不出去，话题改名和拆分这类操作也会被服务端拒绝。所以私有频道创建时顺手把 bot 加进去，是一条必须写进使用说明的运维动作，不能指望它自动发生。
- **可见性只由频道成员身份决定**，不引入额外的按人授权。这既是最小实现，也符合直觉：能进这个频道的人，本来就能看到频道里的一切。给平台再叠一层文件级权限，只会制造两套需要同步维护的真相。
- **附件的访问控制跟随消息**，而不是跟随登录状态。附件挂在消息上，谁能看这条消息，谁就能下载它携带的附件；私有频道里的附件不会因为拿到链接就变成公开的。

这件事给的一条更普遍的教训是：**同一个系统在真实组织里会被用出设计者没想到的用法，而其中一些用法比设计更有生命力。** 上线前所有的讨论都在"怎么让 agent 更有能力"，上线后最先冒出来的需求却是"能不能别让别人看见我"。后者不需要写代码，却决定了有多少人愿意真正用起来。判断这类需求要不要接，标准不是它符不符合原始设计，而是它有没有破坏已有的安全边界——私有频道两者都不违背：它只是把"谁能看见"这个维度显式化了，而边界本来就应该由频道成员身份来定义。

## 11. 提示词与知识的边界

最重要的一条分层：**提示词管行为，知识管事实。** 行为规则常驻（怎么问清楚、什么时候该停、写操作怎么建议），事实与案例走检索（某产品 CLI 有哪些坑、某类报错的判别顺序）。两者失效方式不同——行为靠固定评估集回归，事实靠新故障形态对账。

提示词按代码维护而不按日志追加：新规则优先并入现有条目，总数和字符数有阈值，超过就强制合并重构并跑全量评估。明确**不启用 agent 自进化**：让模型自己改技能、自己写记忆，不可审计不可回滚，还会静默影响之后所有会话。

另一个方向性的结论：**不按领域拆多个专家 agent。** 真实反例很常见——症状落在应用域，根因却在输入形态域（看着像登录问题，实际是密码里的特殊字符）。领域分类是不可靠的深层特征，加一个路由器等于新增一个失败点；反倒是通用 agent 的跨域联想在这个场景里是优势。

## 12. 下一阶段：同一个引擎，两个入口

到目前为止，两条链路的起点都是人：人带着问题来，在话题里问；人被叫醒，去审一张方案。

下一个阶段是让另一类主体也能进入这套系统——**告警**。低风险、可逆、有明确回滚的动作不再等人逐单点头，由接入告警的 agent 自主判断、自主执行；人只在它判断不了、或者动作越过风险线的时候被叫来。

两者不是两套系统，而是**同一个引擎的两个入口**：

|  | ChatOps | 自主运维 |
|---|---|---|
| 起点 | 人带着问题来 | 告警带着现场来 |
| 目标 | 给一个有证据的结论 | 把状态恢复到预期 |
| 谁提问 | 研发、运维 | 没有提问者，触发源是事件 |
| 人在哪 | 对话中 | 事前定策略，事中只处理升级 |

共用的是三段管道，一段都不新写：

- **写操作管道**：还是信封、筛查、只读复核、人工确认、逐字重放。变的只是"人工确认"这一格由谁来填——从逐单人审，变成人预先审定的策略。也就是说，自动化没有把执行权交给模型，而是把人的审批从"每一单"上移到"哪一类单、在什么条件下、可以执行到什么程度"。
- **案例管道**：自主处理的每一次事件和人的每一次排障一样，都进候选池；成稿、判据回流、脱敏摘要，走同一条路。
- **知识管道**：新的判别规则、新的误报模式继续按增量提炼发布，两个入口共用同一份公开知识。

这个方向的关键不是"让 agent 更自主"，而是**把审批粒度从单次升级为策略，同时不丢掉那个锚点**。风险大致这样分：

- 可逆、有回滚、范围明确的沙盒或预发动作：复核通过即执行，配频控、执行前后验证、事后通知，以及一键退回人工的总闸；
- 生产批量、缩容、首次出现的类型：仍然留给人；
- 删除、开放公网、权限与凭据类变更：始终人工，或者只生成方案。

开闸之前有一组前置条件，缺一条都不该开：请求人、复核人、执行确认人的身份要能分别落账（不能只证明 token 归属就声称识别了实际操作人）；失败要停、频控要有上限；总闸必须能一键回到全人工；先跑足够长的影子模式，把自动判断和人工意向逐条比对，结果写成新的架构决策再开。

说明白一点：**这是方向，不是现在的形态。** 风险分层自动执行一直被标注为规划、没有宣称已实现——这个自觉比功能本身更重要。

## 13. 观测与评估

| 层 | 回答什么 | 谁是事实源 |
|---|---|---|
| 业务审计 | 谁问了什么、用了哪些工具、最后回了什么 | 审计库（唯一权威） |
| LLM 观测 | 一轮为什么慢、token 花在哪、工具成败与耗时 | 观测副本，可关闭 |
| 评估 | 改动之后变好还是变坏 | 固定样例集 + 快照 |

几个做法：事件 schema 靠**实弹采样**而不是文档——先真跑一遍看字段存在再写解析，字段缺失一律容忍；导出走异步有界队列、默认关闭，队列满或发送失败就丢弃计数，观测挂了问答和审计照常；不引入 SDK，镜像保持标准库依赖，避免把核心路径绑在某个观测产品的版本上；把提示词文件哈希作为 trace 元数据，就能按"规则集版本"筛选线上调用。评估分三件：确定性断言保下限，LLM-as-judge 查引用忠实度，人工复核抬上限；能用代码判的机械部分（数字、引文是否存在）下沉成断言，只把语义分歧交给模型。

## 14. 拒绝清单

| 候选 | 结论 | 理由 |
|---|---|---|
| 持久化执行框架 | 不引入 | 现有进程、CLI、SQLite、定时任务够用；有状态组件都要增加接手成本 |
| A2A 协议 | 暂不引入 | MCP + 话题已能表达深挖、续接、取消；协议应由场景驱动 |
| 按领域拆多个专家 agent | 否决 | 症状常落在应用域、根因在输入形态域；路由器本身会变成新的失败点 |
| 提示词托管平台 | 不接入 | UI 改完即生效，绕过"改动 → 评估 → 快照"的闸门 |
| 统一注册中心 | 暂不建 | 消费者只有一个；"多 agent 接同一工具网关"已由 MCP 提供 |
| 换 harness | 不换 | 质量已近上限、时延痛点来自上下文长度，换运行时收益接近零 |
| 自研 agent loop | 不写 | 优先用现成运行时 |

还有一条关于"要不要自研胶水层"：如果某个框架的原生适配把**可变会话名当会话键**、**看不到改名事件**、**状态只存在进程内存**，接它等于把刚拆掉的对账层和恢复问题原样买回来。自研的价值不在代码量，而在这些语义归谁定义。

## 15. 五条经验

1. **用稳定标识，别用可变的显示名当主键。** 混用一次，就要养一整套对账逻辑。
2. **边界靠部署位置和凭据范围表达，不靠提示词。** "不许读私有文档"写在提示词里只是愿望。
3. **人审的粒度是确定性产物，不是自然语言指令。** 逐字重放一段命令块，比审一句"给它重启一下"可靠一个数量级。
4. **把模型从执行路径里拿出来。** 诊断可以交给模型，执行不能。
5. **文档是系统的一部分。** 会话、决策、验证证据都落成仓库里的 Markdown，任何接手者——人或 agent——都能只看仓库判断当前状态。

回头看，这套系统的复杂度几乎不在模型：换一个模型，业务逻辑基本不动。复杂度全在三处——话题属于谁、agent 能碰什么、变更谁签字。这三个问题答清楚了，剩下的都是工程。
